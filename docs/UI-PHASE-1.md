# Phase 1 gate: foundation

Phase 1 of `docs/PROMPT-UI.md`, built 2026-11-14. This is the gate report: what exists, how it was checked, and what is not done. Phase 2 waits for approval.

## What was built

| Part | Where | Notes |
|---|---|---|
| Tokens | `web/ui/tokens.css`, generated by `scripts/build-ui.mjs` from `@primer/primitives` 11.10.0 | Only the tokens the stylesheets name, and what those depend on. Five themes: light, dark, dark dimmed, light and dark high contrast. No colour is typed by hand anywhere; a test fails if one is. The package's web font is dropped from the font stack. |
| Icons | `web/ui/icons.js`, generated from `@primer/octicons` 19.42.0 | 91 icons as path data, inlined as SVG. The product mark is its own drawing, not an Octicon. |
| Components | `web/ui/components.js`, `web/ui/ui.css` | The nineteen parts in the study's inventory: header, repository header with tabs, file table, commit row, diff view, timeline item, comment box, label, state badge, button kinds, dropdown, dialog, tab bar, pagination, empty state, flash message, avatar, heatmap, counter. Also form fields with error reporting, side navigation, breadcrumbs. |
| Gallery | `/-/gallery` | Every component on one page, in the account menu. |
| Router | `web/ui/router.js`, `web/sw.template.js`, `web/404.html` | Addresses are paths. The service worker answers a deep link with the pinned page; before it is installed the host's 404 page hands the address over. Works under a path prefix. Scroll position is restored. Addresses the older screens write (`#/name/view`) are translated. |
| Header and footer | `web/ui/chrome.js` | The header shows only what has a screen behind it: the mark, the create menu, the account menu, and "Offline" when offline. Search, Issues, Pull requests, Explore and the bell are built and shown in the gallery, and appear when their screens exist. The footer opens the About dialog, which holds the page's integrity value, and the shortcut list. |
| Themes | Settings → Appearance; `web/ui/theme-init.js` | Follows the system setting until one is chosen. Applied before first paint. |
| First run | `/welcome` | Three steps: a name and email, a sign-in key, then create or open a repository. |
| Screens | `/`, `/new`, `/open`, `/settings/profile`, `/settings/appearance`, `/settings/security`, not-found, error | Home lists repositories with a filter; it is not yet the dashboard (Phase 5). |
| Create a repository | `createRepo` in `web/git.js` | New product logic: a first commit with a README. Its identifiers are checked against git. |
| Strings | `web/ui/strings.js` | Every string of the rebuilt screens. |
| Older screens | `web/app.js`, `web/style.css` | Files, commits, blame, editor and pull requests draw inside the new frame, unchanged in behaviour and wording. Their styles are scoped and use tokens. |

## Checks

`npm test`: 110 tests, 106 pass, 4 skipped (the storage tests that need credentials, as before this phase). 17 are new.

- **In a real browser engine** (`test/ui.test.mjs`, 11 tests; a headless Chromium-family browser driven over its debugging protocol, no test framework added): each screen through its main path and one failure. Landing and not-found; first run with blank and malformed fields; new repository with a bad and a taken name; open repository with a bad and a dead address; settings with validation, theme change and reload; system dark theme; back, forward, reload, deep link and scroll restoration, then a reload with the network off; a path prefix; the gallery in all five themes with dialog, menu and shortcut keys; an older repository screen in the frame with the `g c` and `g p` keys; no sideways overflow at 360 px on eight screens. Every test also asserts the page logged no error.
- **Measured against the study**: 14 px text; 32 px, 6 px radius, 1 px border, weight 500 on the primary button; 40 px file rows. Asserted in the gallery test.
- **Banned-word scan** (`test/words.test.mjs`): no banned word, exclamation mark or Title Case in the strings file; no banned word in any literal of the rebuilt code. It runs in `npm test`, so it fails the `page` check.
- **Generated files are fresh**: the test rebuilds tokens and icons from the pinned packages and compares.

## Budgets

Measured 2026-11-14 on the development machine, viewport 390 by 844, CPU slowed four times as the stand-in for a mid-range phone. Five runs; the machine was doing other work (about 40 percent load), and the runs differ by more than the budgets' margins.

| Budget | Limit | Measured | Met |
|---|---|---|---|
| Script, style and markup, compressed (29 pinned files; the two WebAssembly files excluded) | 300 KB | 86 KB gzip, 74 KB brotli | yes |
| First paint of a cached repository screen | 200 ms | run medians 156, 344, 232, 188, 176 ms; single reloads from 132 to 364 | **not reliably**: three runs of five |
| Navigation inside a loaded repository | 100 ms | run medians 40, 142, 61, 39, 53 ms; single navigations from 20 to 185 | four runs of five |

The first-paint budget is at its limit, not inside it. Before the first paint the page loads three stylesheets and thirteen script files one by one from the service worker; joining them into one file each is the obvious remedy and was not done in this phase.
"First paint" is the browser's first-contentful-paint, which is the frame. The time until the repository's own content is drawn was not measured separately. No real phone was used, and the measurement should be repeated on a quiet machine.

## Side by side

Captures of every new screen at 1280 by 800 and 390 by 844, light and dark, are kept outside the repository (84 files).
There is no reference capture to set beside them: every screen in this phase (first run, new repository, settings, the signed-in header) needs sign-in on GitHub and Gitea, and the study did not sign in. What could be compared was compared by measurement, above.
Known differences from GitHub, all intended: the header is light on light themes (the token `--bgColor-inset`), where GitHub's signed-in header is dark; the mark and name are the product's own; first run replaces sign-up.

## First-time user script

Not done. Phase 1 has no repository workflow to walk ten tasks through; the tasks the prompt lists (find a file, comment on a line, merge) belong to Phases 2 to 4. Three first-run tasks were walked in the browser tests, which is not the same as a person hesitating.

## Not done, not verified

- Accessibility was built in (labels, roles, focus order, focus return, error association, reduced motion) but not audited. No screen reader was used. Contrast relies on the tokens.
- The command palette, `/` search and `t`, `y`, `l`, `b`, `w`, `.`, `c`, `e`, `j`, `k` keys are not present; their screens come in later phases. `?`, `g c`, `g p`, `Ctrl+Enter` and `Esc` work.
- The dimmed and high-contrast themes render and are asserted by background and button colour only.
- The older screens keep their wording. `test/words-baseline.txt` holds the number of their strings with a banned word (18 in `web/app.js`); the test only lets it fall. Messages raised in other modules and shown through those screens are not counted; `docs/UI-STRINGS.md` lists them.
- The older screens can still be reached at `/{name}/...`, not `/{owner}/{repo}/...`. There is no owner yet.
- A slow older screen delays the next navigation until it has drawn, because screens draw one at a time.
- The `page` check now needs a browser on the machine that runs it. That is not declared in `.holo/checks.json` as a tool, so a result made with one browser version is reused for another.
- The sign-in key is the key the product already had, created in the browser. It is not a passkey.
- Tested in one browser engine (Chromium). Not in Firefox or Safari.
- The product name, and whether the 3D-editor picture is a reference for density only, are still open (`docs/UI-STUDY.md`, section 6). The name is one constant in `web/ui/strings.js`.
